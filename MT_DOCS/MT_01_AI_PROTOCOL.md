# MT_01_AI_PROTOCOL.md

> **Как работает ИИ-агент в проекте [MT].** Не про код — про процесс.
> Грузится **всегда**, даже когда код не пишется.
> **История изменений:** `MT_DOCS/CHANGELOG.md`.

## 1. Пять правил (обязательны для всех правок)

1. **Не гадать об API молча.** Если сигнатура или семантика метода не проверена по декомпилу 42.21 — пометить `[?]` в коде или явно написать «предполагаю» в описании. Не выдавать предположение за факт. Проверка: `MT_04_NAVIGATION` §1 (где искать) + запрос конкретного файла.

2. **Искать идиому до примитива.** Перед `setWornItem` — проверить `ISWearClothing`. Перед `AddItem` в обход — проверить `ISInventoryTransferAction`. Перед ручным `resetModel` — проверить, не делает ли это штатное действие. Примитив — только если штатного действия нет, и с комментарием почему. Канон идиом: `MT_02_RULES` §1.1.

3. **Точечный декомпил по запросу.** Если нужен факт по API — просить конкретный файл:
   - **Java-API** → `Java_Decompile/zombie/<полный/путь/Файл>.java` (дерево: `Java_Decompile/Java_Decompile_tree.md`).
   - **Lua-API** → `Lua_Decompile/lua/<client|shared|server>/.../<Файл>.lua` (дерево: `Lua_Decompile/Lua_Decompile_tree.md`).
   Указывать полный путь (`zombie/inventory/ItemContainer.java`, `lua/shared/TimedActions/ISWearClothing.lua`), не только имя класса. Навигация — `MT_04_NAVIGATION` §1.

4. **Список предположений перед кодом.** Перед финальным кодом — 3–4 строки: «знаю точно (по декомпилу / по проекту) / предполагаю / не проверял». Пользователь видит риски до запуска, а не после.

5. **Не изобретать заново.** Если паттерн уже показан (в декомпиле, в предыдущей итерации, в `MT_03_KNOWLEDGE` §3) — использовать его. Не предлагать альтернативу «с нуля» без причины.

## 2. Как грузить доки (не тянуть всё)

### 2.1. Базовое правило

- **Всегда:** `MT_00_INDEX` + этот файл.
- **Дальше — по карте** из `MT_00_INDEX` §2. Не грузи `MT_02`, `MT_03`, `MT_04` «на всякий случай».
- **Если задача не покрыта картой** — сначала `MT_00_INDEX` §2 (может, задача уже есть), потом `MT_03_KNOWLEDGE` §1 (может, симптом уже описан), потом `MT_02_RULES` (может, правило уже есть). Только если нигде нет — писать новое и **добавлять в канон**, а не в ответ.

### 2.2. Обязанность обновлять индекс

При **любом** изменении структуры доков агент **обязан** обновить `MT_00_INDEX`:

| Что изменилось | Куда в `MT_00_INDEX` |
|---|---|
| Новый мод | §3 «Моды проекта» — строка в таблице |
| Новый тип задачи (повторяется 2+ раза) | §2 «Карта задача → файлы» — строка |
| Новый канонический адрес факта | §4 «Правило один факт — одно место» — строка |
| Удалён мод/файл | Удалить строку из §3 / §2 / §4 |
| Изменилась структура папок | §1 «Структура документации [MT]» |

**Формат обновления:** правка в `MT_00_INDEX` + запись в `MT_DOCS/CHANGELOG.md` (что именно добавил/убрал, почему).

**Если агент не может обновить индекс** (файл не в контексте, нет доступа) — он **обязан** явно сказать пользователю: «требуется обновить `MT_00_INDEX` §N, добавить строку: …». Молча оставить рассинхрон — запрещено.

### 2.3. Что агент НЕ делает с индексом

Без **явной** команды пользователя:

- **Не создаёт новый мод** в `MT_MODS/`. Решение «это отдельный мод проекта» — за пользователем. Агент может предложить, но не создать папку и не добавить строку в §3.
- **Не добавляет строку в §2 «Карта задач»** для одноразовой задачи. Строка заслуживается только если задача **реально повторяется** (встретилась 2+ раза в разных сессиях). Иначе карта распухнет до 30 строк и станет бесполезной.
- **Не удаляет строки** из §3 / §2 / §4. Удаление — только по команде пользователя («мод X больше не нужен», «задача Y больше не актуальна»).
- **Не переписывает** §1 «Структура документации» по своей инициативе. Это фундамент, его меняет только пользователь.

Если агенту кажется, что строка устарела — он **предлагает** («строка X в §3 ссылается на удалённую папку, убрать?»), но не удаляет молча.

### 2.4. Проверка рассинхрона (раз в 5–10 задач)

Периодически — пробежать глазами `MT_00_INDEX` и сверить с реальностью:

- [ ] Все моды из §3 имеют папку в `MT_MODS/`?
- [ ] Все файлы из §1 существуют?
- [ ] Все типы задач из §2 ведут на существующие файлы?
- [ ] Все адреса из §4 указывают на реальные подразделы?
- [ ] Записи в `MT_DOCS/CHANGELOG.md` за последние 5–10 задач соответствуют реальности (нет «добавил мод X», где X нет в §3)?

Если нашёл рассинхрон — **явно сообщить** пользователю и предложить правку. Не исправлять молча, если это касается §3 (моды) или §1 (структура).

## 3. Факт / соглашение / паттерн

Три категории, которые агент **обязан различать** в своих ответах:

- **Факт** — проверяемо по декомпилу 42.21. Пример: «`ItemContainer.AddItem` сам вызывает `Remove`» — `ItemContainer.java:215`. Нарушение = баг. Канон: `MT_02_RULES` §1.
- **Соглашение** — договорённость [MT]. Пример: «4 пробела, не табы». Нарушение = замечание на ревью, не баг. Канон: `MT_02_RULES` §2.
- **Паттерн** — проверенный рецепт. Пример: «`ISWearClothing` + `wait = 5` после крафта». Не факт и не соглашение — **рекомендация**. Канон: `MT_03_KNOWLEDGE` §3.

При написании кода агент явно указывает, к какой категории относится его утверждение.

## 4. Что запрещено

- **Копировать факт из канона в ответ или в другой файл.** Если факт нужен — ссылка (`см. RULES §1.2`), не копия.
- **Молча менять канон.** Любая правка `MT_02_RULES` / `MT_03_KNOWLEDGE` / `MT_04_NAVIGATION` / `MT_00_INDEX` — с записью в `MT_DOCS/CHANGELOG.md`. **Per-file Changelog не ведётся.**
- **Писать per-file Changelog.** История — только в `MT_DOCS/CHANGELOG.md`. В файлах — inline-«**Почему:**» там, где правило неочевидно, но не история версий.
- **Плодить файлы.** Порог дробления: файл > 5k токенов **и** в нём выделились 3–4 кластера, которые **никогда** не ищутся вместе. Иначе — не дробить.
- **Удалять из канона** (файлы, строки в индексе, пункты правил) без явной команды пользователя. Добавлять — можно, удалять — нет.
- **Создавать новые моды** в `MT_MODS/` без явной команды пользователя (см. §2.3).

---

## 5. Что считается «фактом», а что «соглашением» (напоминание)

- **Факт** — проверяемо по декомпилу. Можно оспорить, сверившись с `MT_04_NAVIGATION` §1.
- **Соглашение** — договорённость команды. Следуем даже если не понимаем зачем.
- **Паттерн** — рекомендация. Можно предложить альтернативу, если есть причина.

Если агент пишет правило и не уверен в категории — **явно говорит**: «это, кажется, факт, но не проверял по декомпилу» → пользователь либо подтвердит, либо отправит проверять.

## 1. Факты движка (проверяемо по декомпилу 42.21)

> Правила этого раздела **объективны**: либо подтверждены декомпилом, либо это баг. При сомнении — сверяйся с `MT_04_NAVIGATION` §1. Нарушение = баг.

### 1.1. Игровые действия (Критично)

Любое игровое действие — через `IS*Action` классы, а не через прямые мутации:
- Надеть → `ISWearClothing`
- Прикрепить на хотбар → `ISAttachItemHotbar` (или `getPlayerHotbar():attachItem(...)`)
- Переместить → `ISInventoryTransferAction`
- Снять → `ISUnequipAction` / `ISRemoveItemAction`

Прямые вызовы (`setWornItem`, `AddItem` в обход действий) — только если штатного действия нет, и с пометкой `[?]` в коде.

**Что даёт `IS*Action`:** анимация, синхронизация в MP, очередь `ISTimedActionQueue` (не перебивается другими действиями), обновление модели/UI.

### 1.2. Контейнеры и предметы

- **`ItemContainer:AddItem()` атомарен.** Метод **сам** вызывает `item.container.Remove(item)` при успехе (подтверждено декомпилом 42.21, `ItemContainer.java:215`). Явный `Remove` перед `AddItem` создаёт окно потери предмета при отказе `AddItem` — **запрещено**.
- **`AddItem` возвращает `InventoryItem` или `nil`.** Проверять результат: `nil` = предмет не добавлен (перегруз, отказ движка) — логировать.
- **`InventoryItem:getContainer()` может быть `nil`.** Предмет на земле, в руках, на хотбаре — везде `nil`. Перед `getContainer():Remove()` — проверять.
- **Контейнеры vs не-контейнеры.** `getItemContainer()` возвращает `nil` для фляг, ножей, фонарей. Перед переносом — `if item:IsInventoryContainer() then`.
- **`getAllCreatedItems():get(0)` — не всегда нужный предмет.** Если рецепт создаёт несколько выходов — фильтровать по `getFullType()`, а не брать первый.

### 1.3. Worn/Attached предметы

- **Слот worn-предмета — `WornItem:getLocation()`**, а не `InventoryItem:getBodyLocation()`. Последний может вернуть `""` для предметов без явного `BodyLocation`.
- **`getAttachedSlot()`:** `-1` = не прикреплён, `0` = валидный слот хотбара (truthy в Lua). Не путать `nil` и `-1`.
- **`canBeAttached(slot, item)` перед `attachItem`.** Иначе тихий провал без ошибки. Плюс `availableSlot[idx]` может быть `nil` — проверять.
- **`getPlayerHotbar(playerNum)` — только клиент.** На сервере вернёт `nil`. Проверять `if hb then` перед `attachItem`/`removeItem`.

### 1.4. Крафт

- **`OnCreate` ≠ место для мутаций контейнера.** В `OnCreate` — только сбор данных (`getAllCreatedItems`/`getAllConsumedItems`) и снятие старого предмета с персонажа. Перенос содержимого, жидкостей и надевание — в `OnTick` через `wait = 3..5` тиков, когда движок закончил крафт.
- **`syncItemFields` — проверять существование.** `if syncItemFields then syncItemFields(char, item) end`. В SP-сборках функция может отсутствовать.

### 1.5. Жидкости

- **`FluidContainer:copyFluidsFrom()`**, а не `Empty() + addFluid()`. Второй теряет смеси (вода + антисептик и т.п.), оставляя только primary fluid.

### 1.6. Жизненный цикл и тики

- **Тики, а не время.** В `OnTick` — счётчики тиков (`data.ticks = data.ticks - 1`), не `os.time()`. `os.time()` в `OnPlayerUpdate`/`OnTick` — лагодром и рассинхрон между клиентами.
- **`Events.OnTick` и `Pending`.** Каждый элемент `Pending` **обязан** иметь счётчик `ticks` и удаляться по `ticks <= 0` при неудаче. Иначе утечка памяти и «вечные» попытки на каждого крафта.
- **`ModData` — не для временного состояния.** `ModData` сохраняется в сейв. Для «жду 5 тиков после крафта» — локальная `Pending`-таблица, а не `ModData`. Иначе мусор в сейве и баги после перезагрузки.
- **`getSpecificPlayer(playerNum)` на сервере = `nil`.** Все клиентские операции (UI, hotbar, анимации) — под `if isClient() then`. Серверная логика — через `sendClientCommand`.
- **`ISTimedActionQueue` не очищается сам.** Если действие упало — очередь может застрять. Проверять `ISWearClothing:isValid()` перед `add`, не добавлять, если персонаж уже в действии (`ISTimedActionQueue.getCurrentAction`).

### 1.7. UI

- **`ISUIElement` / `ISPanel` не загружены при старте.** Создавать UI-классы отложенно через `Events.OnGameBoot`. Не использовать `.derive` в корне файла — только внутри функции инициализации.
- **`getTimeStep()` не существует.** Использовать `getTimestampMs()` (fallback `getTimeInMillis()`).
- **Drag & Drop:** экранные `getMouseX()`, не `self:getMouseX()`. Все 4 метода: `onMouseMove`, `onMouseUp`, `onMouseMoveOutside`, `onMouseUpOutside` + `setCapture`.
- **`javaObject:DrawTextureAngle(tex, cx, cy, angleDeg, r, g, b, a)` — 8 аргументов.** alpha в **8-м** аргументе, `setAlpha()` игнорируется. Метод не масштабирует текстуру — для разных разрешений нужны отдельные PNG.
- **Масштабирование текста НЕВОЗМОЖНО в B42.21.** `TextManager:DrawStringScaled`, `UIFont.Tiny`, `getTextureManager()` — все `nil`. См. `MT_03_KNOWLEDGE` §2.
- **`keepOnScreen = false`** перед `setX(-500)`, чтобы панель не уезжала за экран.

### 1.8. Файловая система

- **`getFileWriter` allowlist:** только `.ini`, `.cfg`, `.txt`, `.log`. Другие расширения заблокированы движком.
- **Порядок загрузки Lua — ASCII-сортировка.** Символ `.` в ASCII-коде раньше `_`. Значит `MT_File.lua` загружается раньше `MT_File_Data.lua`. Следствие — см. §2.1 (соглашение об именовании).

### 1.9. MP-синхронизация (Критично)

Любая мутация контейнера/предмета в MP требует `sendRemoveItemFromContainer` / `sendAddItemToContainer` / `syncItemFields`. Проверять `isClient()` / `isServer()`. Без этого — десинк и фантомы предметов у других клиентов.

### 1.10. Анимации

- **`RightHandMask` для мили-оружия работает** при использовании подслоя `maskingright` (ванильный подслой B42) и `m_ConditionPriority > 0` в XML. `primaryAnimMask` из скриптов предметов **игнорируется** движком для `HandWeapon`.
- **Имя Action внутри `.fbx` должно совпадать с `<m_AnimName>` в XML.** Движок ищет анимацию по внутреннему имени, а не по имени файла на диске.
- **`ISWalkToTimedAction` не существует в B42.** Ходьба реализована через `ISPathFindAction`. Проверка: `player:isCurrentActionPathfinding()`.
- **Скелет пальцев PZ:** 2 кости на руку (`Finger0`, `Finger1`). Список костей в XML должен быть симметричным, иначе кисть вывернется.

### 1.11. Типы и коллекции

- **`ArrayList` в декомпиле = `ArrayList` в Lua-биндингах.** `:size()`, `:get(i)`, `:add()` — не `#list` и не `list[i]`. Это не Lua-таблица.
- **`instanceof` в Java = `:getFullType()` / `:getType()` в Lua.** Проверка типа предмета — по `getFullType()` (`"Base.TBag1"`). `getClass()` в Lua-биндингах может быть недоступен.

### 1.12. Прочее

- **Пустая строка `""` — truthy в Lua.** `if str then` пропускает `""`. Всегда `if str and str ~= "" then`. Классические грабли на `getBodyLocation()`, `getAttachmentType()`, `getLocation()`.
- **`javaObject:setAlpha(...)` не работает для `DrawTextureAngle`.** См. §1.7.
- **PZ `getFileWriter` allowlist.** См. §1.8.

## 2. Соглашения проекта (договорённости [MT])

> Правила этого раздела — **договорённости команды**. Не проверяются по декомпилу. Нарушение = замечание на ревью, не баг.

### 2.1. Стиль кода

- **Отступы — 4 пробела** (не табы).
- **Комментарии — только по делу** (на русском или английском).
- **Чистый Lua без выделения памяти в `OnPlayerUpdate`** — троттлинг и Weak Tables.
- **`pcall` с логированием** вокруг рискованных вызовов (`AddItem`, `attachItem`, `setWornItem`, `copyFluidsFrom`): `pcall` + `print("[MT] <что>: " .. tostring(err))`. `pcall` — **не замена** правильному API, а страховка от краша.
- **Логи только ASCII в `print()`.** Кириллица — через локализацию, не в консоль.

### 2.2. Обработка ошибок и защита

- **Проверка рук перед снятием/надеванием:** `char:isEquipped(item)` или `char:getPrimaryHandItem() == item or char:getSecondaryHandItem() == item`. Иначе `ISWearClothing` может конфликтовать с предметом в руках.
- **Не мутировать `wornItems` во время итерации.** Собирать индексы/ссылки в таблицу, удалять после цикла. Иначе пропуск элементов и `IndexOutOfBounds` в Java-слое.
- **`resetModel()` — только после смены worn/attached.** Не в каждом тике. После `removeWornItem` — сразу; после `setWornItem` — сразу + `triggerEvent("OnClothingUpdated", char)`.

### 2.3. Работа с состоянием

- **Каждый `Pending`-элемент имеет `ticks`.** Удаляется по `ticks <= 0` при неудаче. Иначе утечка.
- **`ModData` только для сохраняемого состояния.** Временное — в локальных таблицах (см. §1.6).

### 2.4. Формат документации

- **История изменений — в `MT_DOCS/CHANGELOG.md`**, не в этом файле. Per-file Changelog не ведётся. Для неочевидных правил — inline-«**Почему:**» прямо в пункте.
- **Строгая нумерация:** `## 1.`, `### 1.1.`.
- **Обёртка при генерации полного текста файла** — в 4 обратных бэктика (` ````markdown ... ```` `). Внутри есть блоки ```lua и ```ini — тройные бэктики разорвут внешний.
- **Пометки статусов:** см. `MT_00_INDEX` §5.
- **Единый живой документ.** Один файл на тему. Новые находки — в канон, не в мелкие файлы.

### 2.5. Именование

- **Теги — в нижнем регистре** (`mtmw:knife`).
- **ID предметов и файлов — с префиксом `MT_`** (`MT_SmartWatch.txt`, `MT_MeleeStances_Data.lua`).
- **Порядок загрузки** — PZ сортирует полный путь, поэтому числовые префиксы (`_01_`, `_02_`) нужны только внутри одной папки. Если данные и логика разнесены, префиксы не нужны: `MT_Stance/MT_MeleeStances_Data.lua` (`m`) загрузится раньше `MT_Stance/Runtime/...` (`r`). Подпапка `Logic` не подходит: `l` раньше `m`.
- **Java-патчи:** поля и методы, доступные из Lua, — `public`.
- **Лог-префикс в `print()`:** `[MT <ModName>] ...` — для grep, только ASCII.
- **Локализация:** ключи `UI_MT<MOD>_*` в `Translate/{EN,RU}/UI.json`. Trailing comma в JSON обязательна (соглашение, не факт).
- **Файлы конфигов:** только `.ini`, `.cfg`, `.txt`, `.log` (следствие §1.8).
- **FBX-анимации:** имя Action внутри файла = `<m_AnimName>` в XML (следствие §1.10).
